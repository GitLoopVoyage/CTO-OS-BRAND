The central tension

An honest board is the better demo

This is the design problem of the week. Every other decision falls out of how it is resolved.

The controlling distinction — extract section 0

Above every other rule: the visual system may summarise semantic axes but may not substitute one for another.

AuthorityState  ≠  AttemptState  ≠  ExecutionEffect
Authority  ≠  Evidence  ≠  Recommendation  ≠  Disposition
PreAuthorization  ≠  PostEvidenceDisposition
Admissible ≠ LocallyExecutable ≠ ExecutionReserved ≠ ExecutionEffect
External execution claim  ≠  execution proof
Execution proof  ≠  authority
Successful execution  ≠  retroactive authorization

A demo wants a Command Center that looks alive: populated, confident, green. Your rule forbids exactly that — no visual may imply more authority, certainty, verification, safety or runtime state than the model establishes. These pull in opposite directions and the week has to pick one.

Pick the rule. The audience is technical buyers who have been shown all-green dashboards before and know what they are worth. A board that says STALE · last proof 14 d next to UNVERIFIABLE · no runtime attestation is doing something no competitor's demo does: telling the truth about what it cannot see. That is the product thesis rendered as a screen. An all-green board is evidence only that it is a mockup.

Design consequence

Every component gets its UNKNOWN variant designed first, not as an afterthought state. If the unknown variant looks broken or apologetic, the component is wrong. Uncertainty must look deliberate and engineered, because in this product it is the honest answer, not a failure.

Demo-data rule

The reference tenant must be self-evidently synthetic — an invented company, invented services, invented incidents. No screenshot of the demo may be mistakable for a real organisation's real posture. Fabricated data presented as genuine is the same defect class the product exists to prevent.

Corrected by the model extract

An earlier draft of this plan set a target of “roughly a third of the board not settled green.” That is withdrawn. A distribution target is itself a form of fabrication — it makes the picture argue for a conclusion the fixture did not produce. The fixture truth determines the distribution. It is a demo design heuristic when composing the fixture, never a lint rule and never a data quota.

The gate

Canon Lint

Your rule, written as executable checks rather than a paragraph everyone agrees with and then forgets.

Shipped Day 1. canon-lint.js loads a built artifact in a real browser and checks it against computed styles, not source classes — so “visually distinct” and “not styled as an error” are measured rather than asserted. State vocabularies live in canon-vocabulary.json, transcribed from the model extract; the linter reads them at run time and hardcodes nothing.

Rule 10 of the extract — implemented as an absence

No distribution rule exists in the linter and none may be added. The observed settled/unsettled split is printed as NON-NORMATIVE information and can never fail a build. A linter that enforced a quota of doubt would be manufacturing the same false picture as one that enforced a quota of green.

First run — the gate held

Run against the published Fractal Pulse page, which we had already vetted by hand twice. It failed, with ten errors. The most serious was mine:

// full-screen thinking state, as shipped
AUTHORITY   Pending
ASSURANCE   Not yet required

// PENDING is a value on the evidence-presence axis.
// The AuthorityState value is PENDING_VALIDITY.
// This is exactly the axis collapse extract section 0 forbids.

Corrected rather than silenced: the panel now carries exact vocabulary, an as-of on every row, a resolvable evidence reference, and a synthetic-fixture declaration. It is the canon's first compliant surface. Two warnings remain and stay visible — the loader variants named Hold and Complete collide with formal vocabulary on other axes. Scoped as component documentation, not silenced, because the collision is worth knowing about.

Risk

What could cost the week

Named now so the mitigation is designed in rather than improvised on Thursday.

Docs arrive late — closed

The shell needs only two things from the doctrine on Day 1: the eight epistemic values and the six pipeline display stages. Both are already stated in your brief.

Mitigation: Days 1–3 proceed on that minimum. Only the Command Center's content fidelity is exposed, and that is Thursday.

Phase C creep

The Evidence Graph is the most interesting artifact in the canon and will be tempting to start mid-week.

Mitigation: it encodes model claims, so it needs the docs read properly. Starting it Thursday produces a diagram we rebuild. It is week two, first thing.

Demo pressure on Friday

The predictable failure is someone asking for the board to look greener the night before.

Mitigation: the lint gate is mechanical and runs last. It does not negotiate, which is the point of writing the rule as code.

Shell scope

A full design system is three weeks. Two days buys the subset the canon actually consumes.

Mitigation: the shell is scoped by what artifacts 03–18 need, not by component-library completeness. Anything nothing consumes is not built.

Input — received

Model extract v0.1 received and adopted. Next input, needed before Day 4: nothing blocking — the reference tenant will be composed from the extract’s axes alone.
